# Session: очистка собственных Telegram-аккаунтов

Этот репозиторий сохраняет существующий `bot.py`, его очистку, проверку через @SpamBot и завершение других сеансов. Это отдельная версия от проекта `Haha`, не замена исходников на другой бот. Версия диагностики: `cleanup-separate-2`.

## Очистка

1. Напишите `/start` в личном чате бота с разрешённого Telegram ID.
2. Нажмите **«Очистить аккаунт»**. Для новых настроек очистка также выбрана по умолчанию. Ранее сохранённый режим аккаунта не меняется автоматически.
3. Прочитайте список действий. Загрузите свою `.session` или ZIP с парными JSON.
4. Нажмите «Проверить и запустить». Бот снова покажет полный список действий и кнопку **«Подтверждаю действия»**. Только после подтверждения начнётся обработка очереди.
5. Готовые ZIP сохраняются в SQLite до отправки. Отдельные результаты выдаются сразу; при ошибке доставки используйте `/archives`.

Глубокая очистка сбрасывает имя, username, описание и настройки приватности; удаляет фотографии, контакты, папки, стикеры, черновики, Избранное и историю диалогов; выходит из групп и каналов, удаляет каналы создателя и блокирует ботов. Также очищает платёжные данные, завершает веб-авторизации и другие сеансы, устанавливает срок автоудаления аккаунта в 30 дней. Загруженная авторизация сохраняется. Это необратимые действия; отдельные запросы Telegram могут отказать, а отмена не откатывает уже выполненные действия.

Очистка здесь комплексная: выбор отдельных категорий пока не реализован. Если нужен только выход с других устройств без удаления данных, выберите **«Завершить другие сеансы»** — это отдельный режим с собственным подтверждением. Смена режима и новая загрузка отменяют предыдущее подтверждение. Старое подтверждение для другого режима не запускает обработку. Внутри очереди тоже проверяется наличие подтверждения для очистки и завершения сеансов.

Миграция оставлена отдельным режимом, но больше не вызывает очистку, сброс других устройств или `LogOutRequest` старой авторизации — ни после кода, ни после 2FA, ни при финализации. Поэтому ошибка сохранения или доставки новой сессии не приводит к намеренному отзыву исходной авторизации. Миграция не является основным режимом этой версии.

## Railway: один сервис и Volume

- В Railway выберите репозиторий **Afimin128899/Session**, ветку `main`. Сборка через Dockerfile, команда запуска **`python launch.py`**, Root Directory — корень репозитория. Если в настройках осталась команда `python -m sessionbot` от другого проекта, удалите её или замените на `python launch.py`.
- Создайте Volume, смонтируйте в **`/data`**. В Variables задайте `DATA_DIR=/data`. SQLite и временные копии загруженных сессий сохраняются на этом диске. По умолчанию база: `/data/sessions_v100x.db`; её можно переопределить переменной `DB_FILE`.
- Обязательные Variables сервиса: `BOT_TOKEN`, `API_ID`, `API_HASH`, **`ALLOWED_IDS`** — положительные числовые Telegram ID через запятую. Для совместимости поддерживается `ADMIN_IDS`; при наличии обоих приоритет у `ALLOWED_IDS`. Это ID пользователя, не бота, телефона или @username.
- `.env` из репозитория **не загружается**. Используйте только Railway Variables. `.env.example` — образец, не рабочая конфигурация.
- Оставьте **одну replica** и остановите прежний сервис с тем же токеном, включая сервис из `Haha`. Один токен нельзя использовать в нескольких polling-процессах. Локальный диск и SQLite не защищают от копии на другом сервере.
- Публичный HTTP-порт не нужен. Webhook этого токена нужно отключить до polling. Бот проверяет наличие webhook при запуске и не удаляет его автоматически.

После deployment в логе должно появиться имя бота `@...` и сообщение о polling. Откройте именно этого бота и отправьте `/start`. Если ответа нет, проверьте `ALLOWED_IDS`; отказ в доступе записывается без текста сообщения. `Booting VM for replica 1` — только сообщение Railway о запуске контейнера, не подтверждение подключения к Telegram.

Dockerfile копирует только исходники и зависимости. Существующие в репозитории `.env`, каталог `sessions/`, ZIP и базы не входят в образ; реальные аккаунты автоматически не открываются. Однако `.gitignore` и `.dockerignore` не удаляют уже опубликованные файлы из Git или истории. Опубликованные токены/сессии следует считать раскрытыми: замените токен через BotFather, а старые авторизации проверьте в официальном клиенте Telegram. Не добавляйте новые секреты в репозиторий.

## Офлайн-проверки и границы проверки

Python 3.12:

```sh
pip install -r requirements.txt pytest==8.4.2 pytest-asyncio==1.2.0
pytest -q
```

Тесты подставляют синтетические переменные, используют временные базы и поддельные клиенты. Файлы из `sessions/` и настоящие `.env` не читаются. CI запускает те же тесты. Реальный Telegram не подключался. Проверяются очистка, выход из других сеансов, подтверждения, запрет доступа из групп, отсутствие очистки/выхода при миграции, чтение кодов, параллельность и сохранность архивов после ошибок.

Это доработка существующего бота, а не полная реализация всех требований к новой очереди из проекта `Haha`. В частности, сохранённые ручные состояния привязаны к чату; нет отдельного долговременного состояния ввода для каждой задачи, единой блокировки разных сессий одного аккаунта и автоматического срока хранения результатов. Не запускайте несколько файлов одного аккаунта одновременно. Прерванные операции нужно проверять перед ручным повтором: часть изменений Telegram могла уже выполниться. Успешные моки не подтверждают полноту фактической очистки на Telegram.

На собственном тестовом аккаунте отдельно проверьте реальную очистку каждого выбранного типа данных, ограничения Telegram на свежую авторизацию, прокси, рестарт с Volume и выдачу `/archives`. Никто не должен считать очистку полностью проверенной только по офлайн-тестам.
