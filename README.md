# Session: новая авторизация, очистка и выход из старой

Этот репозиторий сохраняет существующий `bot.py`, его очистку, проверку через @SpamBot и завершение других сеансов. Это отдельная версия от проекта `Haha`, не замена исходников на другой бот. Версия диагностики: `new-clean-logout-3`.

## Основной режим: новая сессия → очистка → выход

1. Напишите `/start` в личном чате с разрешённого Telegram ID.
2. Выберите **«Новая сессия → очистка → выход»**. Этот режим используется по умолчанию для новых настроек. Ранее сохранённый режим не переключается автоматически — нажмите кнопку явно.
3. Загрузите собственную исходную `.session` или ZIP с парными JSON. Нажмите «Проверить и запустить», прочитайте полный список действий и нажмите «Подтверждаю действия».
4. Бот войдёт в новую авторизацию. Telegram определяет доставку кода; при необходимости потребуются ручной код и 2FA.
5. Бот проверит соответствие аккаунта, закроет новую SQLite-сессию и сохранит её копию **до очистки**. Затем подключится через новую авторизацию и очистит аккаунт.
6. После очистки он повторно сохранит `.session`, `.json` и ZIP на Volume, выполнит fsync и запишет ZIP в SQLite. **Только после этих действий** отправит `LogOutRequest` загруженной старой авторизации.
7. Новая авторизация останется активной. ZIP выдаётся сразу, а `/archives` позволяет получить его повторно.

В этом режиме **не вызывается сброс всех авторизаций**. Завершается только загруженная старая авторизация; другие созданные новые авторизации этого аккаунта не отзываются. Новые файлы постоянно хранятся в `DATA_DIR/new_sessions/<владелец>/<задача>/before_cleanup/` и `after_cleanup/`, вне временных рабочих копий. Завершение задачи, отмена и ошибка отправки не удаляют эти сохранённые файлы и не вызывают выход из новой авторизации.

Если очистка частичная, новый вход не подтверждён, аккаунт не совпал или запись результата не удалась, бот **не завершает старую авторизацию**. Очередь при ошибке приостанавливается. Уже выполненное удаление данных отмена не восстанавливает. Если сохранение вообще невозможно, рабочая новая сессия оставляется на диске для восстановления. Если ZIP сохранён в файлах, но SQLite временно не принимала запись, `/archives` попробует восстановить запись из файлов только этого владельца после устранения ошибки диска. Неподтверждённый выход из старой авторизации сообщается отдельно; повторов выхода в обход FloodWait нет.

При обычной миграции (без комбинированного режима) очистка и выход из исходной авторизации по-прежнему не выполняются. Отдельная кнопка «Очистить аккаунт» использует загруженную авторизацию и не создаёт новую. Отдельный режим «Завершить другие сеансы» отзывает все остальные авторизации, поэтому не выбирайте его, если требуется сохранить другие новые авторизации.

## Что удаляет комплексная очистка

Глубокая очистка сбрасывает имя, username, описание и настройки приватности; удаляет фотографии, контакты, папки, стикеры, черновики, Избранное и историю диалогов; выходит из групп и каналов, удаляет каналы создателя и блокирует ботов. Также очищает платёжные данные, завершает веб-авторизации и устанавливает срок автоудаления аккаунта в 30 дней. Отдельный режим очистки через исходную авторизацию дополнительно завершает другие сеансы; комбинированный режим этого не делает.

Это необратимые действия. Перед обработкой отображается перечень и требуется подтверждение. Выбор отдельных категорий пока не реализован. Telegram может отклонить отдельные запросы; это не считается полной подтверждённой очисткой. Новая загрузка и смена режима отменяют предыдущее подтверждение. Комбинированные задачи выполняются по одной на чат, чтобы вручную введённые коды и 2FA не пересекались.

## Railway: один сервис и Volume

- В Railway выберите репозиторий **Afimin128899/Session**, ветку `main`. Сборка через Dockerfile, команда запуска **`python launch.py`**, Root Directory — корень репозитория. Если в настройках осталась команда `python -m sessionbot` от другого проекта, удалите её или замените на `python launch.py`.
- Создайте Volume, смонтируйте в **`/data`**. В Variables задайте `DATA_DIR=/data`. SQLite и временные копии загруженных сессий сохраняются на этом диске. По умолчанию база: `/data/sessions_v100x.db`; её можно переопределить переменной `DB_FILE`.
- Обязательные Variables сервиса: `BOT_TOKEN`, `API_ID`, `API_HASH`, **`ALLOWED_IDS`** — положительные числовые Telegram ID через запятую. Для совместимости поддерживается `ADMIN_IDS`; при наличии обоих приоритет у `ALLOWED_IDS`. Это ID пользователя, не бота, телефона или @username.
- `.env` из репозитория **не загружается**. Используйте только Railway Variables. `.env.example` — образец, не рабочая конфигурация.
- Оставьте **одну replica** и остановите прежний сервис с тем же токеном, включая сервис из `Haha`. Один токен нельзя использовать в нескольких polling-процессах. Локальный диск и SQLite не защищают от копии на другом сервере.
- Публичный HTTP-порт не нужен. Webhook этого токена нужно отключить до polling. Бот проверяет наличие webhook при запуске и не удаляет его автоматически.

После deployment в логе должно появиться имя бота `@...` и сообщение о polling. Откройте именно этого бота и отправьте `/start`. Если ответа нет, проверьте `ALLOWED_IDS`; отказ в доступе записывается без текста сообщения. `Booting VM for replica 1` — только сообщение Railway о запуске контейнера, не подтверждение подключения к Telegram.

Dockerfile копирует только исходники и зависимости, включая модуль сохранения новых сессий `session_results.py`. Существующие в репозитории `.env`, каталог `sessions/`, ZIP и базы не входят в образ; реальные аккаунты автоматически не открываются. Однако `.gitignore` и `.dockerignore` не удаляют уже опубликованные файлы из Git или истории. Опубликованные токены/сессии следует считать раскрытыми: замените токен через BotFather, а старые авторизации проверьте в официальном клиенте Telegram. Не добавляйте новые секреты в репозиторий.

## Офлайн-проверки и границы проверки

Python 3.12:

```sh
pip install -r requirements.txt pytest==8.4.2 pytest-asyncio==1.2.0
pytest -q
```

Тесты подставляют синтетические переменные, используют временные базы и поддельные клиенты. Файлы из `sessions/` и настоящие `.env` не читаются. Для тестов используются только искусственные байтовые файлы. CI запускает те же тесты. Реальный Telegram не подключался. Проверяются очистка, выход из других сеансов, подтверждения, запрет доступа из групп, отсутствие очистки/выхода при миграции, чтение кодов, параллельность и сохранность архивов после ошибок.

Это доработка существующего бота, а не полная реализация всех требований к новой очереди из проекта `Haha`. В частности, сохранённые ручные состояния привязаны к чату; нет отдельного долговременного состояния ввода для каждой задачи, единой блокировки разных сессий одного аккаунта и автоматического срока хранения результатов. Не запускайте несколько файлов одного аккаунта одновременно. Прерванные операции нужно проверять перед ручным повтором: часть изменений Telegram могла уже выполниться. Успешные моки не подтверждают полноту фактической очистки на Telegram.

На собственном тестовом аккаунте отдельно проверьте реальную очистку каждого выбранного типа данных, ограничения Telegram на свежую авторизацию, прокси, рестарт с Volume и выдачу `/archives`. Никто не должен считать очистку полностью проверенной только по офлайн-тестам.
